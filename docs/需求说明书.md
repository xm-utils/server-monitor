## 一、项目概述

### 1.1 项目背景
当前 CashLoan 业务下的服务器及 Docker 容器服务数量持续增长，运维与研发缺少一个轻量、单机即可部署的实时指标查看工具。现有方案（如 Prometheus + Grafana）部署较重，不适合小规模、快速排查问题的场景。

本项目旨在构建一个 **单二进制、轻量部署** 的 Go 服务（HTTP 服务复用团队内部库 `github.com/xm-utils/tools/grpcx`，统一响应复用 `github.com/xm-utils/tools/common`），用于采集所在服务器的整体运行指标，以及服务器上运行的 Docker 容器服务指标，并通过 HTML 模板在浏览器中可视化展示，辅助研发与运维快速定位问题。

### 1.2 项目目标
1. 提供 **服务器整体运行指标** 的实时采集与展示（CPU、内存、磁盘、网络、负载、进程等）。
2. 提供 **Docker 服务运行指标** 的实时采集与展示（容器列表、CPU、内存、网络、磁盘 IO、状态等）。
3. 提供 **基于 HTML 模板的 Web 展示页面**，无需前端工程即可访问。
4. 支持 **HTTP JSON 接口**（基于 `github.com/xm-utils/tools/grpcx` 提供的 HTTP 服务），统一使用 `github.com/xm-utils/tools/common` 的 `Response` 响应格式，便于后续接入告警或第三方系统。
5. 部署简单：单个可执行文件 + 配置文件即可启动。

### 1.3 项目范围
- ✅ 在本期范围内：
  - 单机本地服务器指标采集
  - 本机 Docker Engine 指标采集
  - Web HTML 页面展示（服务端渲染）
  - JSON 指标接口
  - 指标周期性采样与内存历史缓存
- ❌ 不在本期范围内：
  - 多机集中采集 / Agent-Server 架构
  - 持久化存储（MySQL/InfluxDB/Prometheus 等）
  - 告警通知（邮件、钉钉、企微）
  - 用户权限体系与登录鉴权
  - 历史趋势的长期存储与回溯查询

### 1.4 术语定义
| 术语 | 说明 |
| --- | --- |
| 服务器指标 | 指宿主机（Host）层面的系统运行指标 |
| Docker 指标 | 指通过 Docker Engine API 获取的容器级别运行指标 |
| 采样周期 | 一次指标采集的时间间隔 |
| 视图（View） | HTML 页面中呈现的一个监控模块 |

## 二、用户角色与使用场景

### 2.1 目标用户
| 角色 | 关注点 |
| --- | --- |
| 后端研发 | 排查服务 CPU/内存占用、容器是否异常 |
| 运维工程师 | 快速查看服务器整体健康状态、容器运行状态 |
| 技术负责人 | 巡检机器资源水位、判断是否需要扩容 |

### 2.2 典型使用场景
1. **场景一：线上故障排查**
   研发收到报警后登录机器，浏览器打开 `http://<host>:<port>/` 即可查看当前 CPU、内存、磁盘、网络水位，并进入 Docker 页签查看哪个容器占用异常。
2. **场景二：日常巡检**
   运维将页面挂在浏览器中，周期自动刷新，观察服务器整体趋势。
3. **场景三：接口对接**
   上游监控系统通过 `GET /api/metrics/system` 拉取一次快照数据，纳入外部告警。

## 三、功能需求

### 3.1 功能结构图

```
server_monitor_service
├── 指标采集模块（Collector）
│   ├── 系统指标采集器（SystemCollector）
│   └── Docker 指标采集器（DockerCollector）
├── 容器操作模块（Operator，启停/重启）
├── 数据存储模块（Store，内存环形缓存）
├── Web 服务模块（grpcx HTTP Server，基于 gin）
│   ├── HTML 模板渲染（html/template）
│   └── JSON API（common.Response 统一响应）
└── 配置管理（Config）
```

### 3.2 功能列表（Functional Requirements，FR）

| 编号 | 功能名称 | 描述 | 优先级 |
| --- | --- | --- | --- |

| FR-02 | 系统指标采集 | 周期采集 CPU/内存/磁盘/网络/负载/进程/系统信息 | 高 |
| FR-03 | Docker 指标采集 | 通过 Docker API 获取容器列表与每个容器的实时资源占用 | 高 |

| FR-06 | Web Docker 页 | HTML 展示所有 Docker 服务运行指标 | 高 |
| FR-07 | JSON API | `/api/metrics/system`、`/api/metrics/docker` 等对外接口 | 中 |
| FR-08 | 自动刷新 | 页面支持前端定时刷新（默认 5s） | 中 |
| FR-09 | 容器详情查看 | 点击容器查看单容器指标、镜像、启动时间、端口 | 中 |

### 3.3 功能详细说明

#### FR-01 配置文件加载
- 默认读取 `/etc/server_monitor_service/config.yaml`，其次读取当前目录 `config.yaml`。
- 支持通过环境变量覆盖（前缀 `SMS_`，如 `SMS_LISTEN_ADDR`）。
- 关键配置项：
  ```yaml
  server:
    listen_addr: ":8080"          # HTTP 监听地址
    read_timeout: 10s
    write_timeout: 30s
  collector:
    system_interval: 3s           # 系统指标采集周期
    docker_interval: 5s           # Docker 指标采集周期
    history_size: 300             # 内存保留的采样条数
  docker:
    endpoint: "unix:///var/run/docker.sock"  # Docker API 地址
    timeout: 3s
    operations:                              # FR-13 容器启停/重启/重建
      enabled: false                         # 默认关闭，需显式开启写操作
      default_timeout: 10s                   # stop/restart 默认宽限期
      allow_labels: []                       # 仅允许带指定 label 的容器（空=不限制）
      deny_names: []                         # 禁止操作的容器名/ID 黑名单
      compose_command: "docker compose"      # redeploy：compose 命令前缀（旧版可写 docker-compose）
      docker_bin: "docker"                   # redeploy：删除镜像使用的可执行文件
      compose_file: ""                       # redeploy：容器无 compose 标签时的回退 yml 路径
      redeploy_timeout: 5m                   # redeploy：单条命令超时
  log:
    level: info
    format: text
  web:
    refresh_interval_ms: 5000
    template_dir: "./templates"
    static_dir: "./static"
  ```

#### FR-02 系统指标采集
采集内容详见 **第四章 4.1 系统指标定义**。实现要点：
- 基于 `github.com/shirou/gopsutil/v4` 采集（跨平台）。
- 单次采集封装为 `SystemSnapshot`，采集失败时不影响其他字段，失败字段标记为 `unavailable`。
- 采集协程按 `system_interval` 周期运行。

#### FR-03 Docker 指标采集
- 基于 `github.com/docker/docker/client` 连接 Docker Engine。
- 使用 `ContainerList` 获取运行中容器（可扩展至全部）。
- 使用 `ContainerStats`（stream 模式）获取实时 CPU/内存/网络/磁盘 IO。
- 采集结果封装为 `[]DockerSnapshot`。
- Docker 不可用（socket 不存在 / daemon 未启动）时：
  - 服务不中断，Web Docker 页展示 "Docker 未连接" 提示。
  - `/health` 中 `docker.status = unhealthy`。

#### FR-04 指标内存缓存
- 使用环形数组（Ring Buffer）保留最近 `history_size` 条采样。
- 系统指标与 Docker 指标各自独立缓存。
- 读取时返回按时间升序排列的切片，用于 HTML 页面绘制简易趋势图（本期通过内联 SVG / 折线图占位实现，不引入重型前端库）。

#### FR-05 Web 首页（概览）
- 路由：`GET /`
- 渲染方式：Go `html/template` 服务端渲染。
- 页面区块：
  1. 顶部：服务器基本信息（主机名、OS、内核、启动时间、运行时长）。
  2. 仪表盘卡片：CPU 使用率、内存使用率、磁盘使用率、Load1/5/15。
  3. 网络流量：上行/下行速率、累计字节数。
  4. 进程概览：Top N CPU / Top N 内存进程列表。
  5. 趋势区：最近 5 分钟 CPU / 内存迷你曲线。

#### FR-06 Web Docker 页
- 路由：`GET /docker`
- 页面内容：
  1. 容器列表表格：名称、镜像、ID、状态、启动时间、CPU%、内存（占用/限制）、网络 RX/TX、块设备读/写。
  2. 支持按 CPU / 内存 / 名称排序。
  3. 支持按状态（running/exited/paused）过滤。
  4. 点击行进入 `GET /docker/{id}` 详情。

#### FR-07 JSON API
| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/metrics/system` | 返回最新一次系统指标快照 |
| GET | `/api/metrics/system/history?limit=100` | 返回系统指标历史 |
| GET | `/api/metrics/docker` | 返回所有容器最新指标 |
| GET | `/api/metrics/docker/{containerId}` | 返回单容器指标 |
| GET | `/api/health` | 服务健康检查 |
| GET | `/api/version` | 返回构建版本 |

响应统一使用 `github.com/xm-utils/tools/common` 库的 `Response` 结构体：
```go
// common.Response 统一响应结构
type Response struct {
    Code    int32       `json:"code"`
    Message string      `json:"message"`
    Data    interface{} `json:"data,omitempty"`
}
```
- 成功：`common.GinSuccess(c, data)` → `code = 200`（`common.SuccessCode`），`message = "操作成功"`。
- 失败：`common.GinError(c, code, message...)`，HTTP 状态码固定为 200，业务错误通过 `code` 表达。
- `Response` 结构不含 `timestamp` 字段；如需返回时间戳，放入 `Data` 中。

```json
{
  "code": 200,
  "message": "操作成功",
  "data": { }
}
```

#### FR-08 自动刷新
- 模板中根据 `web.refresh_interval_ms` 注入 JS `setTimeout(() => location.reload(), n)`。
- 可通过 URL `?refresh=0` 关闭自动刷新。

#### FR-09 容器详情
- 展示单容器的 Stats、Env、Mounts、PortBindings、NetworkSettings。
- 展示最近 `history_size` 条采样曲线。

#### FR-10 服务健康检查
- 判断条件：
  - 最近一次系统采集时间 < `3 × system_interval`。
  - 最近一次 Docker 采集时间 < `3 × docker_interval`（若 Docker 未启用则跳过）。

#### FR-11 优雅关闭
- 复用 `grpcx.Server` 提供的优雅关闭能力（`ImplementShutdown` / `Server.Stop()`），并监听系统信号：
  1. 收到 SIGINT/SIGTERM 后，停止接收新 HTTP 请求（grpcx 内部调用 `http.Server.Shutdown`）。
  2. 通知采集协程退出（context.Cancel）。
  3. 等待进行中请求结束（超时 10s）。

#### FR-12 日志
- 统一使用 `github.com/sirupsen/logrus`（与 grpcx / common 保持一致）。
- 采集错误、Docker 连接状态变化、HTTP 访问日志分别打点。

#### FR-13 容器启停 / 重启 / 重建操作
面向运维快速干预与部署场景，允许在 Web 页面对单个 Docker 容器执行启动 / 停止 / 重启，以及基于 docker compose 的重建/重新部署。

**操作能力**
- 基于 Docker Engine API 实现：
  - 启动：`client.ContainerStart(ctx, id, types.ContainerStartOptions{})`
  - 停止：`client.ContainerStop(ctx, id, container.StopOptions{Timeout: *timeout})`
  - 重启：`client.ContainerRestart(ctx, id, container.StopOptions{Timeout: *timeout})`
- **docker compose 兼容**：对于 compose 管理的服务，重启单个容器与 API 等效；如需整服务级别 `docker compose restart <service>`，可通过可执行的 compose 模式实现（默认关闭）。

**页面交互**
- Docker 列表页（FR-06）每行、容器详情页（FR-09）均提供【启动 / 停止 / 重启 / 重建】按钮。
- 根据容器当前状态置灰不可用项（如 running 不显示启动）。
- 点击弹出**二次确认**（显示容器名与动作），确认后发起 POST 请求；成功后提示并延时刷新列表状态。
- 操作进行中按钮置为 loading，避免重复提交。

**API**（写操作，统一使用 `common.Response`）
| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/docker/{containerId}/start` | 启动容器 |
| POST | `/api/docker/{containerId}/stop` | 停止容器（可传 `timeout`） |
| POST | `/api/docker/{containerId}/restart` | 重启容器（可传 `timeout`） |
| POST | `/api/docker/{containerId}/redeploy` | 重建/重新部署（停止→删容器→删镜像→拉新镜像→启动） |

请求体（stop/restart 可选）：`{ "timeout": 10 }`（秒，宽限期）。
返回示例：
```json
{ "code": 200, "message": "操作成功", "data": { "containerId": "a1b2c3", "action": "restart", "state": "running" } }
```

**安全与约制**（写操作重点）
- 默认关闭：需 `docker.operations.enabled: true` 才注册上述路由与页面按钮；未启用时访问返回 `code=403`。
- 容器白名单：可配置 `allow_labels` / `deny_names`，仅允许操作符合规则的容器，避免误停关键容器。
- 建议仅本机监听 + 反向代理鉴权（见第十一章风险）。
- **审计日志**：每次操作记录时间、来源 IP、容器 ID/名、动作、结果（成功/失败），使用 logrus 输出。
- 幂等：对已停止容器执行 stop / 对运行容器执行 start 不报错，返回当前实际状态。

**重建 / 重新部署（redeploy）**
面向“部署新镜像”场景，对单容器执行：**停止 → 删除容器 → 删除镜像 → 拉取新镜像 → 启动**。
- 实现方式：通过 `os/exec` 调用 `docker compose`（而非 Engine API 逐步 create），以复用 compose 文件中声明的 env/挂载/端口/网络，避免手工复刻容器配置。
- **compose 文件来源**：优先读取容器 inspect 标签 `com.docker.compose.project.config_files`、`com.docker.compose.project.working_dir`、`com.docker.compose.service`、`com.docker.compose.project`；若缺失则回退到配置 `docker.operations.compose_file`；两者都无则返回错误。
- **仅删该服务镜像**：删镜像前先检查该镜像（按名/ID）是否仍被其他容器使用；若共用则跳过删除，避免影响其他服务；删除失败亦为非致命（不中断重建）。
- **执行日志展示**：接口在 `data.log` 返回每一步命令输出；页面新增结果面板（`#op-result`）展示 redeploy 日志，并通过 sessionStorage 跨自动刷新保留（成功/失败/进行中分色）。
- 前置：宿主机已安装 `docker` CLI 且服务进程有权限；可用 `compose_command`（如旧版 `docker-compose`）、`docker_bin`、`redeploy_timeout` 调整。
- 同样受 `docker.operations.enabled` 开关、白/黑名单、二次确认与审计日志约束；接口服务端超时按 `5×redeploy_timeout` 放宽。

### 4.3 展示阈值（用于 HTML 颜色标记）

| 指标 | 正常 | 警告 | 危险 |

| 磁盘使用率 | < 80% | 80%~90% | ≥ 90% |
| Load1 / 核数 | < 1 | 1~2 | ≥ 2 |
| 容器 CPU% | < 100% | 100%~200% | ≥ 200% |

## 五、非功能需求（NFR）

| 编号 | 类别 | 要求 |
| --- | --- | --- |
| NFR-01 | 性能 | 单次系统采集耗时 ≤ 200ms；服务常驻内存 ≤ 100MB |
| NFR-02 | 性能 | Web 首页渲染 TTFB ≤ 300ms（本地访问） |
| NFR-03 | 可靠性 | 任一采集器异常不影响其他采集器与 Web 服务 |
| NFR-04 | 可用性 | 服务 7×24 运行，Docker 掉线后可自动重连 |
| NFR-05 | 兼容性 | 支持 Linux/macOS；生产主要面向 Linux（CentOS 7+/Ubuntu 20.04+/Debian 11+） |
| NFR-06 | 安全性 | 默认仅监听本机；提供配置项可放开；不支持公网裸奔 |
| NFR-07 | 可维护性 | 核心接口 Collector/Store/Server 可插拔；新增一类指标只需实现 Collector 接口 |
| NFR-08 | 部署 | 输出单一二进制 + `templates/` 静态目录，支持 `systemd` 部署 |
| NFR-09 | 可观测性 | 自身 `/metrics`（可选）或 `/api/health` 反映运行状态 |
| NFR-10 | 文档 | 提供 README、部署说明、指标字典 |

### 6.4 HTML 展示方案

### 6.6 grpcx 与 common 集成说明

本项目不自建 HTTP 监听，而是通过 `grpcx` 装配 HTTP 服务，并在 handler 中使用 `common` 的统一响应。

- **启动 HTTP 服务**：使用 `grpcx.WithHTTPServer(name, addr, httpSetup)` 创建一个 `IServer`，`httpSetup` 接收一个 `*gin.Engine`，在其中注册路由、加载模板、挂载静态资源；再交给 `grpcx.NewServer([]grpcx.IServer{...})` 统一 `Start()`。
- **统一响应**：所有 `/api/*` JSON 接口通过 `common.GinSuccess(c, data)` / `common.GinError(c, code)` 返回 `common.Response`；HTML 页面仍用 `c.HTML(...)` 渲染。
- **优雅关闭**：`grpcx.Server` 实现了 `ImplementShutdown`，HTTP 服务停止时会自动 `Shutdown`；main 中监听信号后调用 `Stop()`。

参考装配伪代码（仅示意，非最终实现）：
```go
httpSrv := grpcx.WithHTTPServer("monitor", cfg.Server.ListenAddr, func(e *gin.Engine) {
    e.LoadHTMLGlob("templates/*")
    e.Static("/static", "static")
    e.GET("/", handler.Index)          // 系统概览页（HTML）
    e.GET("/docker", handler.Docker)   // Docker 页（HTML）
    e.GET("/api/metrics/system", handler.APISystem)  // 返回 common.Response
    e.GET("/api/metrics/docker", handler.APIDocker)
    // FR-13 写操作：仅当 docker.operations.enabled 时注册
    e.POST("/api/docker/:id/restart", handler.DockerRestart)
})
srv := grpcx.NewServer([]grpcx.IServer{httpSrv})
_ = srv.Start()
```

handler 使用 `common` 返回示例：
```go
func APISystem(c *gin.Context) {
    snap := store.System().Latest()
    common.GinSuccess(c, snap) // -> {"code":200,"message":"操作成功","data":{...}}
}
```

## 十一、风险与约束

| 风险 | 影响 | 应对方案 |
| --- | --- | --- |
| Docker API 权限不足 | 无法获取容器指标 | 部署文档明确要求加入 `docker` 组或以 root 运行；健康接口显式暴露状态 |
| 高频采集导致 CPU 上升 | 采集器本身影响被监控机 | 采集周期最小 1s；默认 3s；单次采集有超时保护 |
| 内存缓存无限增长 | OOM | 固定环形数组大小，配置项 `history_size` 有上限 |
| 跨平台差异（macOS/Linux） | 指标缺失或不准 | 使用 gopsutil 屏蔽差异；macOS 仅作为开发环境验证 |
| 无鉴权 | 误暴露到公网导致信息泄露 | 默认 `127.0.0.1` 监听；README 强调生产应通过 Nginx + Basic Auth 或反向代理 |
| 容器启停为写操作，误操作影响业务（FR-13） | 可能误停关键服务 | 默认 `docker.operations.enabled=false` 关闭；白名单/黑名单限制；页面二次确认；全量审计日志；建议配合鉴权使用 |
